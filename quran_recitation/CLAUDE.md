# ربط فاحص التلاوة بالموقع الحالي

الهدف أن يسمّع الزائر بصوته، ثم يرى الكلمة والحركة المتوقعة وما رجّحه الصوت وزمنها. المحرك في quran_checker.py، والواجهة والخادم في هذا المجلد. اعتمد نتيجة المحرك الصوتي كما وصلت، وأظهر «يحتاج إلى مراجعة» عند ضعف الصوت. حافظ على تصميم الموقع القائم.

## إضافة الخدمة

1. افحص إطار عمل المشروع واستضافته. إذا كان فيه خادم FastAPI بالفعل، يمكن تركيب التطبيق كمسار فرعي. ثبّت اعتماديات pyproject.toml في بيئة الخادم واختر مساراً متاحاً، مثلاً:

   ```python
   from quran_recitation.service import app as recitation_app
   app.mount("/quran", recitation_app)
   ```

   يصبح رابط صفحة التجربة /quran/recitation/ ورابط التحليل /quran/api/recitation/analyze. تُحمّل خدمة مركّبة النموذج عند الطلب الأول. خادم مستقل يحمّله عند بدء التشغيل.

2. عند وجود واجهة JavaScript أو استضافة ساكنة، شغّل خدمة Python منفصلة كعملية دائمة. من مجلد quran_recitation شغّل:

   ```sh
   uv run python service.py
   ```

   يفهم الخادم PORT وHOST. عنوان الاستماع الافتراضي 127.0.0.1 والمنفذ 8000. في منصة حاويات اضبط HOST=0.0.0.0 والمنفذ المطلوب للمنصة. يعمل على CPU مع عامل واحد. يستهلك النموذج وحده نحو 2.42 GB على القرص، بالإضافة إلى حزم التشغيل. خصّص ذاكرة تناسب تحميل الأوزان ومعالجة الصوت. يمكن تثبيت مسار مخبأ دائم في HF_HOME أو تمرير QURAN_MODEL_DIR لنموذج محلي. عند نقل الملفات لخادم جديد احتفظ بمجلد assets مع service.py وquran_checker.py.

3. صِل المسار من نطاق الموقع إلى خادم الفحص عبر وكيل الخادم الموجود. مرّر بايتات الصوت، Content-Type ومعاملات الرابط وحالة HTTP ومتن JSON. راع حدود حجم الطلب والمهلة في الاستضافة. إذا كانت الخدمة خلف خادم الموقع، يمكن ضبط QURAN_API_TOKEN وتعيين رأس Authorization: Bearer على الخادم فقط. عند تفعيل المفتاح استخدم مسار الموقع الوسيط في الواجهة. استعمل آلية دخول الزوار وحدود الاستخدام الموجودة في المشروع. الملفات المؤقتة تُزال بعد معالجة الطلب.

## إضافة قسم التسميع

استخدم صفحة /recitation/ كمرجع أو ضمّن العنصر التالي في الصفحة المناسبة من المشروع. المساران هنا يفترضان أن الخدمة مركّبة تحت /quran، أو أن الوكيل يحوّل هذين المسارين لها.

```html
<quran-recitation endpoint="/quran/api/recitation/analyze"></quran-recitation>
<script type="module" src="/quran/recitation/quran-widget.js"></script>
```

تُظهر الواجهة إشعار الفحص الآلي قبل الإرسال. يمكن للزائر رفع M4A أو MP3 أو WAV أو WebM، أو تسجيل مقطع وإيقافه قبل إرساله. يستخدم الميكروفون HTTPS أو localhost. بعد الفحص يستطيع سماع موضع الملاحظة في تسجيله. لتكييف النمط استخدم متغيرات CSS المعرّفة في العنصر مثل --quran-accent و--quran-surface. في واجهات React ونحوها حمّل الوحدة مرة في المتصفح ثم استخدم العنصر.

## عقد الطلب والنتيجة

POST /api/recitation/analyze يستقبل الملف مباشرة في جسم الطلب مع نوعه الصوتي. الحكم افتراضياً على الكلمات فقط (طلب صاحب المشروع): ملاحظة عند تغيّر حروف الكلمة أو سقوطها أو زيادة كلمة، من دون الحركات والتنوين والشدة والمدود والتجويد والصفات، والحروف المتقاربة تُعامل حرفاً واحداً. أضف harakat=1 (أو --harakat في سطر الأوامر) للتقرير الكامل. يذكر الحقل judged أيهما استُخدم (words أو full). يمكن تمرير ayah=1:7 أو ayah=1:2-4. يمكن إضافة words=3-4 مع تحديد آية واحدة. عند ترك ayah فارغاً يحاول المحرك التعرف التلقائي. يحلل الطلب تسجيل قارئ واحد بحجم أقصاه 24 MiB ولمدة لا تتجاوز خمس دقائق. عند انشغال المحرك يُرجع 429 وتعليمات لإعادة المحاولة. عند تعذّر قراءة الملف أو ضعف الصوت يرجع 422 مع detail، وقد يردّ المقطع القابل للفحص بنتيجة review. يرجع GET /health الجاهزية.

```sh
curl -X POST 'http://127.0.0.1:8000/api/recitation/analyze?ayah=1:2' \
  -H 'Content-Type: audio/mp4' --data-binary @voice.m4a
```

في results اعرض حالة كل مقطع، reference_text، ثم findings إن وجدت. ضمن كل ملاحظة استعمل word وexpected وheard وnear_s. في ambiguous اطلب اختيار آية من candidates. تعني no_difference_detected أن المحرّك لم يجد اختلافاً في الأجزاء التي فحصها. ضع إشعار notice في الواجهة عند تخصيصها. جرّب الملف الصوتي عبر مسار الموقع النهائي وافحصه على الآيفون. تحقق من قبول التسجيل، ظهور النتيجة والتعامل مع رفض إذن الميكروفون.
